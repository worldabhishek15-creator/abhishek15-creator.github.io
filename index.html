SIEM · Detection Engineering

SOC Home Lab: SIEM Monitoring and Threat Detection

A virtual SOC with a Wazuh SIEM server and Windows + Linux agents, used to simulate real attacks, verify alerts, map them to MITRE ATT&CK and write incident reports.

Objective

Build an environment that works like a small SOC so I can practise the full analyst workflow end to end: data collection, detection, triage, investigation and reporting.

What I built

  • A virtual SOC lab with a Wazuh SIEM server and Windows and Linux agents collecting endpoint logs.
  • Sysmon on the Windows endpoint for detailed process and system telemetry.
  • Kali Linux machine used to simulate attacker behaviour.
  • Simulated attacks: SSH brute force, failed logins and suspicious PowerShell activity, then verified that detection alerts fired.
  • Mapped detected events to MITRE ATT&CK techniques.
  • Wrote custom detection rules to reduce false positives.
  • Triaged alerts and documented findings in incident reports (root cause, severity, recommended actions).

Tools

WazuhSysmonKali LinuxWindowsLinuxMITRE ATT&CK

Lab architecture

Endpoints send their logs to the Wazuh manager through agents. The manager decodes the logs, runs them against rules and raises alerts that an analyst reviews on the dashboard.

Kali LinuxAttacker machine
→
Windows + LinuxVictim endpoints with Wazuh agent (+ Sysmon on Windows)
→
Wazuh ManagerLog collection, decoding, rules
→
DashboardAlerts, triage, reports

Why these components

  • Wazuh agents forward Windows event logs and Linux authentication logs to the manager.
  • Sysmon adds process creation, network and registry visibility that normal Windows logs do not provide.
  • Kali Linux gives a controlled way to generate realistic attack traffic inside an isolated lab.

Attack simulation → detection → ATT&CK mapping

Simulated activityLog sourceMITRE ATT&CK
SSH brute force from KaliLinux authentication logsT1110 Brute Force
Repeated failed loginsWindows Security / Linux auth logsT1110 Brute Force
Suspicious PowerShell activitySysmon process creation + Windows logsT1059.001 PowerShell
Illustrative mapping of the scenarios above to standard ATT&CK technique IDs.

Tuning for fewer false positives

  • Reviewed which alerts were noisy (for example, a single mistyped password).
  • Wrote custom rules so alerts fire on patterns such as many failures in a short time, instead of on every single event.
  • Re-ran the simulations to confirm real attack behaviour still triggered an alert after tuning.

How I document an incident

  1. Detection: which rule fired, when, on which host.
  2. Investigation: related logs, source IP, targeted accounts, whether the attempt succeeded.
  3. Root cause: what activity caused the alert (e.g. brute-force attempt against SSH).
  4. Severity: assessed using impact and likelihood.
  5. Recommended actions: for example block the source IP, enforce strong passwords or key-based SSH, enable account lockout, keep monitoring.

Splunk · SPL · Dashboards

Log Analysis and Brute-Force Detection Dashboard

Windows Security and Linux authentication logs ingested into Splunk, with SPL searches, a dashboard and a scheduled alert to catch brute-force behaviour faster.

Objective

Detect brute-force and credential-guessing activity from authentication logs, and give the SOC a dashboard and an alert to triage it quickly.

What I did

  • Ingested Windows Security logs (Event ID 4624 / 4625) and Linux authentication logs into Splunk.
  • Wrote SPL queries to detect repeated failed logins, suspicious source IPs and account-lockout patterns.
  • Built a dashboard and a scheduled alert for real-time monitoring and faster alert triage.

Tools

SplunkSPLWindows Event LogsLinux auth logs

Data flow

WindowsSecurity log: 4624, 4625
→
Linuxauth log: SSH / sudo / login
→
SplunkIndex + search (SPL)
→
Dashboard + AlertTriage view

Key Windows events

  • 4625 – an account failed to log on (main brute-force signal).
  • 4624 – successful logon (a success right after many failures is a red flag).
  • 4740 – account locked out.

Example: failed Windows logins by source IP

index=main sourcetype="WinEventLog:Security" EventCode=4625
| stats count AS failed_attempts dc(Account_Name) AS targeted_accounts by Source_Network_Address
| where failed_attempts > 5
| sort - failed_attempts

Example: SSH failures on Linux

index=linux sourcetype=linux_secure "Failed password"
| rex "from (?<src_ip>\d{1,3}(?:\.\d{1,3}){3})"
| stats count AS failures by src_ip
| where failures > 5
| sort - failures
Example queries to show the approach. Index, sourcetype and field names depend on your Splunk setup and add-ons.

Dashboard panels

  • Failed logins over time (spot spikes).
  • Top source IPs by failed attempts.
  • Most targeted user accounts.
  • Account-lockout events.

Scheduled alert

A saved search runs on a schedule and triggers when failed attempts from a source cross a threshold, so the analyst gets notified instead of watching the dashboard all day.

Analyst value

  • Faster triage: the top offenders are visible immediately.
  • Clear starting point for investigation: source IP, targeted accounts and timeline.
